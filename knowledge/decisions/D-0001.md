# D-0001 — Capability beats profile; `resolve` is one function

**Decision**: `RangedWeapons.resolve(stack)` consults the `WEAPON` item
capability first and the `weapons` data map second, and that order is written
out in the one function rather than left to providers registered in event
order. A provider may return null to decline a stack, and the profile tier then
answers. Inside the native tier the data map still supplies what the gun mod
does not expose (spread, engagement range, sounds), so packs retune a natively
supported gun without touching its mod.

**Why**: Code that knows the item beats data describing it — the same
precedence NeoForge uses for an item's own burn time over the furnace-fuels
data map. A gun mod's capability provider knows the stack's real ammunition,
bullet effects and per-stack overrides; a profile is a description written by
someone else. Making the order explicit in one function means the answer is
identical whichever mods are loaded and in whatever order they registered,
which a chain of capability providers on the same item cannot promise: their
order depends on cross-mod event dispatch.

**Alternatives rejected**: *A catch-all capability provider registered on every
item that reads the data map* — precedence then depends on registration order
against other mods' providers, and NeoForge's `ItemCapability` has no priority.
*Profile beats capability* — a pack could silently replace a gun mod's own
bullets with generic tracers on a gun the mod supports natively; wrong by
default. *No profile tier at all* — every gun mod would need code to be
usable, which excludes closed-source ones entirely (see D-0002, D-0003).

**Follow-ups**: A gun mod that wants the data map to *not* override its
spread would need a flag on the profile; none has asked.
