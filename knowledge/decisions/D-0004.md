# D-0004 — Profiles reference items and sounds by id; the loud failure is restored at reload

**Decision**: `WeaponProfile` holds `Optional<ResourceLocation>` for its
ammunition, magazine and sounds, not `Holder`s. The codec is pure
DataFixerUpper. What that gives up — a hard datapack load error on an id that
resolves to nothing — is put back by the mod on `DataMapsUpdatedEvent`, which
checks every profile's ids against the item and sound registries and logs one
actionable warning per bad one, naming the weapon, the field, the id and what
will silently not happen.

**Why**: Ids keep the value types testable in plain JUnit with no bootstrapped
registry (the codec tests run in under a second and boot nothing), and keep a
profile decodable in contexts where the registries are not yet frozen. But a
typo in `"ammo"` must not become "kills drop nothing" discovered a week later;
the check at reload is the one moment the data is known and the registries are
complete, and a warning that says `weapon profile for anothergunmod:revolver
names ammo anothergunmod:smal_bullet, which is not registered; kills will drop
no ammunition` is what a server admin needs.

**Alternatives rejected**: *`Holder`s via `RegistryOps`* — loud at load, but
the codec then needs a registry access and the tests need a booted game; the
plan's own caveat ("`ResourceLocation` may need bootstrap") turned out not to
bite, so the cheap tier stayed cheap. *Fail the reload on a bad id* — a
mis-typed sound id would take the whole datapack down with it, which is a
worse outcome for a server than a silent sound.

**Follow-ups**: The validator has not yet been exercised with a bad id in an
automated test; every shipped id resolves. A gametest datapack with one wrong
id would close that.
